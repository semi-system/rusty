# App passwords

Status: **built** (migration 0052, 2026-11-24).

## What and why

A person gives their mail program on a phone, a laptop or a script a password of its own instead of the password of the account. When the phone is lost, that one password is revoked and nothing else changes; the account's own
password is typed in a browser only. This is also the way mail programs will keep working when two-factor sign-in is added to the webmail (a program cannot answer a second factor).

## Rules

* An account has at most **10** app passwords. Each has a label (1 to 60 characters: "Phone", "Backup script").
* The mail protocols (IMAP, POP3, SMTP submission) accept an app password **besides** the account's own password. The webmail and the admin web do **not**: they build their authenticator without them, so a password
  given to a program cannot open a mailbox in a browser, change settings or make another app password.
* A password is generated by the server: sixteen characters from an alphabet without look-alikes (`abcdefghjkmnpqrstuvwxyz23456789`), in four groups (`abcd-efgh-jkmn-pqrs`, about 79 bits), from the operating system's
  random source. It is **shown once**, in the answer that makes it; only its Argon2id hash is stored (the same hash as for a password).
* Making one needs the account's own password again (`confirm`: the same checks and the same throttle as a sign-in, without a session), so a stolen browser session cannot mint a password that outlives it.
* Revoking is one at a time (`DELETE /api/v1/app-passwords/{id}`), and a person can only revoke their own. Removing the account removes them (`ON DELETE CASCADE`).
* A login with an app password notes `last_used_at` (a write that never stops or slows the login), so the person can see which ones are still in use.
* Brute force is as for passwords: the protocol services throttle by address and by account before they check anything; the extra hashes (at most ten) are checked only after the account's own password did not match.

## Where it lives

* `app_passwords` (migration 0052) and `AppPasswordRepo` (`create`, `list`, `hashes`, `touch`, `revoke`).
* `LocalAuthenticator::with_app_passwords`: used by `rusty_svc::Context` (every protocol service); the webmail and the admin web use the plain authenticator.
* Webmail API: `GET /api/v1/app-passwords`, `POST /api/v1/app-passwords` (`{label, password}` answers `{id, label, secret}`), `DELETE /api/v1/app-passwords/{id}`.
* Database roles: `rusty_webmail` may read, insert and delete the rows; `rusty_imap` and `rusty_submission` may read them and update `last_used_at`; no other role touches the table.

## Not yet

* A screen in the web front end (the API is there), an admin action to revoke all of an account's app passwords, and scopes (an app password for IMAP only).
* Two-factor sign-in for the webmail (needs a key for the shared secrets; its own design).
