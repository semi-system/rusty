# Own host names for a customer's domain (webmail and admin)

Status: **design, for approval** (2026-11-25). Decided by the owner: a domain gets **two fields**, a *webmail host* and an *admin host*; the certificates are ordered by the edge **by itself** (Let's Encrypt, HTTP-01) once the
customer has pointed the name at the platform.

## 1. What it is for

A customer who adds `capturer.io.vn` to the platform wants their people to open `https://mail.capturer.io.vn` (the webmail) and their administrators `https://admin.capturer.io.vn`, not the platform's names.
Today everyone uses the platform's `MAIL_HOST` (webmail and mail clients) and `ADMIN_HOST`; a domain has no host names of its own (`docs/first-mail.md`).

Out of scope: IMAP and SMTP stay on the platform's mail host (the edge ends TLS for 993 and 465 with the mail host's certificate; the ports that start in plain text, 143 and 587, present the service's certificate of that
one name, so a customer name there would not match). The auto-setup answers (`autoconfig`, Autodiscover, the Apple profile) keep naming the mail host for IMAP and SMTP, and name the domain's **webmail host** where they link to the webmail.

## 2. The model

Migration `0060_domain_hosts.sql`: table `domain_hosts (domain_id PK references domains ON DELETE CASCADE, webmail_host text NULL, admin_host text NULL, webmail_state text, admin_state text, updated_at)`.

* A host is a DNS name in lower case (the rules of `valid_host`), at most 253 characters; unique across the table (a partial unique index on each column, and a check that the two of one domain differ).
* It is **never** one of the platform's own names (`MAIL_HOST`, `ADMIN_HOST`, `WEBMAIL_HOST`, the name servers): the admin service refuses it, and the edge would too.
* `*_state` is `pending` (saved, the DNS does not point here yet), `dns_ok` (it does; the certificate is being ordered) or `ready` (the edge has a certificate for it). The edge's report sets it (section 5).
* Grants: `rusty_admin` reads and writes the table; `rusty_webmail` reads it (section 6); the edge sync reads it through the admin service (section 5), not with a database role of its own.

## 3. Admin API and page

`PUT /api/v1/domains/{domain}/hosts` with `{"webmail_host": "...", "admin_host": "..."}` (an empty string removes one), `GET` returns them with their state. **Platform administrators only** at first: every host is a certificate order against
the platform's edge, and the people who may claim names should be few (a later step may let a domain administrator set them, within a quota). The domain page of the admin web gets the two fields and, under each, the DNS record
to publish and its check, like the records of the DNS page.

## 4. DNS

For each host the customer publishes a `CNAME` to the platform's mail host (or an `A`/`AAAA` at the edge's addresses). The DNS check engine (`rusty-core::dns_check`) gets the two records as a new kind, `Requirement::Required` for a host that
is set, with the purpose "Your webmail address" / "Your admin address". The check compares addresses, so a CNAME or an A record passes alike (as the `autoconfig.` record does). A host whose check is not `Ok` is `pending`: **no certificate is ordered
for it**, which keeps failed orders out of the authority's limits (the same rule as the wait before `init`, `docs/swarm-runbook.md`). The orders count against the customer's own registered domain, not the platform's.

## 5. The edge

The edge's configuration is generated by the Manager's tool (`rusty-swarm`), and the edge cannot reload itself from the database. So:

* The admin service answers `GET /internal/edge/hosts` on its backend address only: the hosts with `dns_ok` or `ready`, as JSON, bearer token from a Swarm secret (`edge_hosts_token`), never published at the edge.
* `rusty-swarm hosts sync` (and a systemd timer every minute, like `certs install-timer`) reads that list, and **when it changed** writes the tenant part of the edge configuration and reloads the edge without dropping connections:
  * **HAProxy** (the default): one `crt-store` entry with `acme letsencrypt domains` per host, a `.lst` file per kind (`webmail-hosts.lst`, `admin-hosts.lst`) and `use_backend be_webmail if { hdr(host),lower,field(1,:) -f ... }` / `be_admin` for the admin hosts (with `ADMIN_ALLOW`, section 7). The reload is the master process's `SIGUSR2` (a seamless reload), by `docker exec`.
  * **Prost** (`EDGE=prost`, `prost-certd`): the same list becomes `listeners.tls.certificates` entries and routes, and the certd's domain list. Prost's reload story is the open question of section 9.
* It reports back, `PUT /internal/edge/hosts/state` (same token), which hosts have a certificate: `ready`.
* Port 80 is already open to the edge (the challenges and the autoconfig); nothing else changes in the firewall.

## 6. The webmail

`public_origin` is one name today (`[webmail] public_origin` and `extra_origins`). The origin check (`guard_mutation`, `pre_auth_guard`) learns a set that **the webmail reads from `domain_hosts`** (a cache of 60 seconds; a name that is not in it
is refused as before). The session cookie is `__Host-`: a host-only cookie, so a session opened on one host is valid on that host alone. People sign in with their full address on any of the hosts (the host does not
decide which account), as they do on the platform's.

## 7. The admin web on a customer's admin host

The same service answers on the host. What it shows is cut to the domain: **a session opened on a customer's admin host is limited to that domain's administrators** (the grants of `domain_admin_grants`); the platform pages and the
platform administrators' sign-in are refused there (a `403`), so the customer's host never becomes a way to the platform's controls. The network allow-list (`ADMIN_ALLOW`) is the platform's: it does not suit customers, so a
customer admin host is **open to the internet** and guarded by the sign-in, the throttle and the second factor. This is the part that needs the owner's agreement (section 9).

## 8. Steps (each a pull request with tests)

1. Migration, store (`DomainHostsRepo`), grants and the matrix test; the admin API and the page; the DNS records and their check.
2. The internal list and report endpoints, and `rusty-swarm hosts sync` for HAProxy (scenarios in `scripts/tests/swarm-stack.sh`).
3. The webmail's origin set; the auto-setup answers name the webmail host.
4. The admin web's scoping on a customer's admin host.
5. Prost.

## 9. For the owner to decide

* **Who may set the hosts**: platform administrators only (proposed), or domain administrators too within a quota?
* **Customer admin hosts and `ADMIN_ALLOW`**: open to the internet behind sign-in, throttle and second factor (proposed), or a per-domain allow-list the customer fills in?
* **Prost**: HAProxy first (proposed; a seamless reload exists), Prost when its reload or API for a changing list is known?
