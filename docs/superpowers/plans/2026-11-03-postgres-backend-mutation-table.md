Each mutation was judged first by the test binaries that plausibly cover it and, if that did not kill it, by the full judging suite. The baseline (hook compiled in, no mutation selected) was green.

Not covered: NOT NULL constraints, column defaults and identity definitions, and the bodies of trigger functions (they are exercised by the behaviour suites but never mutated).

Survivors carry a written waiver (one line per id in `scripts/pg-mutate-waivers.tsv`, no wildcards) for the reviewer to accept or reject; a survivor without one is printed as UNEXPLAINED and fails the committed-table test.

## Survivors

- dialect `D08-unnest-insert-unordered` (WAIVER proposed): change_log unnest insert loses its ORDER BY. Equivalent: change_log rows are keyed by (mailbox_id, seq) and the seq comes from the t.seq column of the unnest, never from insertion order; the mailbox row is locked FOR UPDATE first, so no concurrent writer shares the (mailbox, seq) range, and every read (CHANGES) orders by seq. The physical order of the insert is unobservable through the repository.
- dialect `D09-blob-insert-unordered` (WAIVER proposed): batch blob insert loses its ORDER BY (the ascending lock order). Redundant second line of defence: lock_blobs builds a BTreeMap, so the arrays bound to the statement are already ascending and the SQL ORDER BY cannot change the lock order for any reachable input. The forced-crossing knob tests do NOT kill it (that knob replaces the whole path); blob_lock_order_matrix_has_no_deadlock_and_exact_refcounts exercises the production path with rotated and reversed inputs and would notice a lost ordering only if the BTreeMap were also removed. Gap: nothing mutates the BTreeMap itself (PG8 carry-over).
