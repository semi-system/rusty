## Survivors

- dialect `D08-unnest-insert-unordered` (WAIVER proposed): change_log unnest insert loses its ORDER BY. Equivalent: change_log rows are keyed by (mailbox_id, seq) and the seq comes from the t.seq column of the unnest, never from insertion order; every read orders by seq, so the physical order of the insert is unobservable through the repository.
- dialect `D09-blob-insert-unordered` (WAIVER proposed): batch blob insert loses its ORDER BY (the ascending lock order). Redundant second line of defence: lock_blobs builds a BTreeMap, so the arrays bound to the statement are already ascending and the SQL ORDER BY cannot change the lock order for any reachable input. The ascending-order rule itself is killed by the forced-crossing controls in pg_mailbox_concurrency (unordered_blob_locks knob deadlocks) and by mutation D09 not being reachable otherwise.
- dialect `D12-account-insert-do-nothing` (WAIVER proposed): ON CONFLICT DO NOTHING added to the account insert (a duplicate address no longer errors). Equivalent: the BEFORE INSERT trigger accounts_addr_unique_ins runs before the unique index is checked and raises RS001 for any address already in the registry, and the registry coincides with the accounts (local_part, domain_id) unique key, so ON CONFLICT DO NOTHING on the accounts insert is never reached by a duplicate. The sibling D11 (list members, where no trigger pre-empts the unique index) is killed.
- dialect `R08-gc-shard-listing-empty` (WAIVER proposed): the GC shard listing returns nothing. Redundant by design: the orphan phase re-checks row absence with blob_row_exists immediately before deleting each file, so an empty shard listing cannot make GC delete a referenced blob (it only makes the orphan sweep skip rows); the file of a referenced blob is protected twice. The row-deleting half of GC is judged by R07 and the gc suites.
