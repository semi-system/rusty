# Edge (HAProxy, option A) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the hardened public entry container using HAProxy (user decision 2026-11-03: HAProxy first; fall back to the `tlsd` layer later if this does not hold up), with a Compose skeleton, fake backends, a hardening checker, and a product-agnostic behaviour test suite that decides whether HAProxy meets the requirements.

**Architecture (option A):** HAProxy is the only container that publishes ports. Implicit-TLS mail ports (465 SMTPS, 993 IMAPS, 995 POP3S) are terminated at HAProxy with certificates loaded from files (`crt-list`, SNI selection, default cert policy) and re-encrypted with verified mTLS to the backend. STARTTLS ports (25, 587, 143, 110) are TCP pass-through; the backend service does STARTTLS with its own certificate. HTTPS (443) is terminated by HAProxy in HTTP mode (assumption pending user confirmation, see edge spec §8). Mail ports use PROXY protocol v2 to the backend so services see the real client IP. This supersedes `2026-11-03-edge-skeleton.md` (Traefik), which must NOT be executed.

**Tech Stack:** Docker/Compose (Docker, rootless where possible), HAProxy (resolve the current stable/LTS image at implementation time, record the version and release date, pin by digest — do not invent a version), Rust (backends, checker, behaviour tests), rustls, Pebble + challtestsrv (ACME test servers; only needed once `certd` exists, so ACME is OUT of this plan).

**Specs:** `docs/superpowers/specs/2026-11-03-rusty-edge-tls-layer-design.md` (decision update §0), `docs/superpowers/specs/2026-11-03-rusty-container-deployment-design.md` (§4 hardening, §3b.3b service-side abuse controls, §5 transports).

## Global Constraints

- Only the `edge` (HAProxy) container publishes ports; no service mounts a container-runtime socket; no `privileged`, no host networking; every container: non-root uid, `read_only: true`, `cap_drop: [ALL]` (edge may add only `NET_BIND_SERVICE` if it binds < 1024; prefer high ports + host mapping), `no-new-privileges`, memory/cpu/pids limits, healthcheck.
- HAProxy configuration is static, mounted read-only; no stats/admin socket reachable from outside any container; if the runtime API socket is enabled it is a Unix socket on a private tmpfs with mode 0600 used only by the edge's own tooling; no stats page published.
- TLS: minimum TLS 1.2 (prefer 1.3), modern ciphers only, `ssl-min-ver` set explicitly, one shared TLS policy block for all terminated ports; session resumption policy explicit (tickets off, or rotated keys — document and test); unknown/absent SNI behaviour explicit and tested.
- Mail backend links: `verify required` with a pinned internal CA, a client certificate from the edge (mTLS), and PROXY v2. If the pinned HAProxy cannot do TLS to a backend together with PROXY v2 in the order the backend expects, STOP and report; never silently fall back to plaintext or to an unverified backend (the pasted nginx example did not verify the backend; do not copy that).
- Abuse controls at the edge (supplement, never a replacement for the services' own, spec §3b.3b): per-source-IP concurrent connection limit and connection-rate limit with a stick-table, short client handshake and idle timeouts, bounded total connections, protocol-aware backend health checks.
- Images pinned by digest in `deploy/images.lock` (script prints and verifies digests). Test certificates are generated by a script into an untracked directory (keys 0400, dirs 0700); nothing secret is committed. ACME is out of scope (needs `certd`).
- All checks run offline after images are pulled; the checker exits non-zero on the first violation and prints which rule failed.
- Verified-behaviour rule: the HAProxy manual is large and was only partially read when this plan was written. BEFORE writing config, the implementer reads the relevant manual sections (bind options incl. `ssl`, `crt`, `crt-list`, `strict-sni`, `ssl-min-ver`, `ciphersuites`, `no-tls-tickets`; server options incl. `ssl`, `verify`, `ca-file`, `crt`, `send-proxy-v2`, `sni`; stick-tables and `tcp-request connection`; timeouts; `tcp-check`; runtime API `set ssl cert`/`commit ssl cert`; master-worker reload) from the docs of the pinned version and records the verified facts with quotes in `deploy/VERIFIED.md`. Anything not confirmed there must be proven by a behaviour test.

## Review Focus

- A compose file in which ANY service other than the edge publishes a port, mounts a runtime socket, is privileged, uses host networking, or runs as root must fail the checker (bad fixtures).
- The edge must not silently accept an unverified backend: backend certificate wrong CA / wrong name / expired / missing client-cert requirement must break the connection, never pass traffic.
- PROXY header spoofing: a client sending its own PROXY header must not influence the source IP the backend sees.
- Pass-through ports must not alter bytes (binary round trip) and STARTTLS must upgrade end to end with the backend's own certificate.
- Unknown SNI / no SNI behaviour must be explicit and tested; SNI values must never reach a file path.
- Per-IP limits really limit (flood from one IP is capped while a second IP is unaffected); slowloris style connections are closed within the configured time on EVERY port type.
- Certificate rotation: replacing a certificate (reload or runtime API) must not drop established connections, and the old certificate must stop being served afterwards.
- Private keys: never in an image, env var, log, `docker inspect` output, or persistent disk; only on read-only tmpfs mounts.
